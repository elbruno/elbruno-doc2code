# Plan: API Key Middleware Authentication

**Created:** 2026-02-08 11:27 AM  
**Status:** Completed  
**Complexity:** Low (~1 hour)

## Goal

Add a shared API key validated by middleware on all `/api/*` and SignalR routes across the ApiService and SettingsService. The Blazor Web frontend and service-to-service calls inject the key automatically via HTTP headers and SignalR query strings.

## Steps

### 1. Define `ApiKeyAuthOptions` in ServiceDefaults

Add a new file `ApiKeyAuth.cs` in the `elbruno.Doc2Code.ServiceDefaults` project (both ApiService and SettingsService already reference it).

- Class: `ApiKeyAuthOptions` with a `string Key` property
- Constant: header name `X-Api-Key`
- Extension method: `AddApiKeyAuth(this IHostApplicationBuilder, string configSection = "ApiKey")` — reads the key from config and registers the options
- Extension method: `UseApiKeyAuth(this WebApplication)` — applies the middleware

### 2. Create `ApiKeyMiddleware` in ServiceDefaults

A new middleware class that:

- Reads the expected key from `ApiKeyAuthOptions`
- Skips validation for `/health` and `/alive` endpoints
- Checks the `X-Api-Key` header on all other requests
- For SignalR/WebSocket requests, also checks `?access_token=` query parameter (browsers can't set headers on WebSocket upgrades)
- Returns `401 Unauthorized` if the key is missing or incorrect
- If no key is configured (empty/null), **bypasses validation entirely** — preserves zero-config local dev experience

### 3. Wire middleware into ApiService

In `src/elbruno.Doc2Code.ApiService/Program.cs`:

- Call `builder.AddApiKeyAuth()` after `AddServiceDefaults()`
- Call `app.UseApiKeyAuth()` before `app.MapDoc2CodeRoutes()`

### 4. Wire middleware into SettingsService

In the SettingsService `Program.cs`:

- Same two calls: `builder.AddApiKeyAuth()` and `app.UseApiKeyAuth()`

### 5. Configure the key in AppHost

In `src/elbruno.Doc2Code.AppHost/Program.cs`:

- Add a parameter: `var apiKey = builder.AddParameter("apikey", secret: true)`
- Pass it as an environment variable to all three services: `.WithEnvironment("ApiKey", apiKey)`
- Aspire manages the secret (prompts on first run, stores in user secrets)

### 6. Inject the key into Web → ApiService HTTP calls

In `src/elbruno.Doc2Code.Web/Program.cs`:

- Add a `DelegatingHandler` (e.g. `ApiKeyDelegatingHandler`) that reads `ApiKey` from `IConfiguration` and adds the `X-Api-Key` header to every outgoing request
- Register it on both `AddHttpClient<SettingsApiClient>(...)` and `AddHttpClient<GenerationApiClient>(...)`

### 7. Inject the key into Web → ApiService SignalR

In `src/elbruno.Doc2Code.Web/Services/AgentLogSignalRService.cs`:

- Modify the `HubConnectionBuilder` `.WithUrl(...)` call to append `?access_token={key}` to the URL, or use the overload that accepts headers configuration

### 8. Inject the key into ApiService → SettingsService HTTP calls

In `src/elbruno.Doc2Code.ApiService/Program.cs`:

- Register the same `ApiKeyDelegatingHandler` on the `AddHttpClient<RemoteSettingsClient>(...)` call so service-to-service calls also carry the key

### 9. Update `.gitignore`

Ensure any local secrets files generated by Aspire (typically in `~/.microsoft/usersecrets/`) are not committed. Verify Aspire's `appsettings.*.json` patterns are covered.

### 10. Update documentation

Add an "Authentication" section to `docs/security.md` explaining:

- How the API key is configured (Aspire parameter or `ApiKey` env var)
- That auth is opt-in (empty key = no auth, for local dev)
- How to set a key for network-exposed deployments

## Verification

- Run `dotnet build` on the solution to confirm no compile errors
- Start the Aspire app host — on first run it should prompt for the `apikey` parameter
- With a key set: verify `curl http://localhost:<port>/api/settings` returns `401`, and the Blazor UI still works normally
- With no key set: verify everything works without auth (backward compatible)
- Run existing tests in `tests/` to confirm no regressions

## Design Decisions

| Decision | Rationale |
|---|---|
| Middleware in ServiceDefaults | Both ApiService and SettingsService need the same logic — avoid duplication |
| Opt-in (empty key = no auth) | Preserves frictionless local dev; security only activates when a key is configured |
| Aspire `AddParameter(secret: true)` | Leverages Aspire's built-in secret management rather than hardcoding keys |
| `X-Api-Key` header + `access_token` query param | Header for HTTP, query param for SignalR WebSocket upgrade (standard pattern) |
| `DelegatingHandler` for outgoing HTTP | Cleanest way to inject headers into typed `HttpClient` registrations without touching every call site |

## Endpoints Protected

### ApiService

| Method | Route | Purpose |
|---|---|---|
| POST | `/api/generate` | Start code generation |
| GET | `/api/generate/{runId}/status` | Poll generation status |
| GET | `/api/generate/{runId}/download` | Download generated archive |
| POST | `/api/generate/{runId}/github` | Publish to GitHub |
| POST | `/api/settings/test-connection` | Test LLM connection |
| SignalR | `/hubs/agent-log` | Real-time agent log streaming |

### SettingsService

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/settings/` | Fetch current config |
| PUT | `/api/settings/` | Replace entire config |
| PATCH | `/api/settings/tools` | Toggle individual tools |
| GET | `/api/settings/models/suggested` | Get model recommendations |

### Excluded (health checks, dev-only)

- `GET /health`
- `GET /alive`
